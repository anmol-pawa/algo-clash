# Algo Clash: Architecture

How the game is built. Decisions that are expensive to reverse are recorded as ADRs in `docs/adr/NNNN-title.md` (context, options, decision, consequences). Write one whenever you make such a decision.

## 1. Stack

- **Next.js 16** (App Router, static export for GitHub Pages under `basePath` `/algo-clash`), **React 19**, **TypeScript strict**.
- **PixiJS 8** for the overworld, battle stage and sprite effects. React for menus, panels and the editor.
- **CodeMirror 6** with `@codemirror/lang-cpp` (and the vim keymap as an option). Autocomplete is toggleable per mode.
- **Tailwind 4** for UI chrome (as in Query Clash).
- **State:** a small store (zustand or a reducer + context; pick one and record an ADR). Game state is serialisable.
- **Persistence:** IndexedDB (via `idb` or a small wrapper) for the save file, attempt history and code drafts. Versioned schema with migrations and tests. JSON export/import.
- **Offline:** the service worker generated by `scripts/gen-sw.mjs` (from Query Clash, keep the worker-fragment fix). The large toolchain assets are cached on demand, not precached.
- **Tests:** Vitest (unit, content), native C++ verification (g++/clang in Node child processes), and Playwright (Chromium at `/opt/pw-browsers`) for e2e smoke tests and screenshots.

## 2. In-browser C++ judge

### 2.1 Toolchain
Primary candidate: **`@yowasp/clang`** (Clang/LLD built for WebAssembly, targeting `wasm32-wasip1`). The npm tarball is about 27 MB, about 105 MB unpacked, and it **ships libc++ headers and `libc++.a` for wasm32-wasip1** (verified on 2026-10-28 by listing the package). It runs clang in a virtual filesystem via `runClang(['clang++', …], files)`, and the output is a WASI module.

**The spike (ROADMAP A2) must measure and record in an ADR:**
- cold download size over the wire (gzip/brotli)
- cold and warm compile time for a 60-line STL-heavy solution on desktop Chromium and on an iPhone 14 (Safari)
- peak memory
- whether exceptions work (`-fexceptions` with this libc++ build; if not, document that `stoi` on bad input aborts, and make the harness never rely on exceptions)
- the stack size flag (`-Wl,-z,stack-size=…`, needed for deep recursion: 64 MB is a reasonable start; check it actually takes effect)
- `-O2` vs `-O1` compile/run trade-off
- whether `<bits/stdc++.h>` needs the shim (it does: libc++ has no such header, so ship our own `bits/stdc++.h` that includes the standard headers)

**Fallbacks**, if iPhone memory or time makes it unusable:
- (a) desktop-only compiled battles, with mobile limited to cards, Parsons and cloze, plus "Paper mode": write the code and self-grade against the reference after a diff view
- (b) another WASM clang distribution (Wasmer's clang package, or binji's wasm-clang approach)

Never fall back to a C++ *interpreter* that lacks real STL semantics; it would teach wrong behaviour.

**Speed-ups to try:**
- precompile the harness and frequently used headers (a PCH, if supported) once per session
- keep the clang module instantiated in a long-lived worker
- compile only the user's translation unit, then link against a cached harness object

**A2 result (ADR 0001):** `@yowasp/clang` works in a Chromium worker. Exceptions do **not** link (compile with `-fno-exceptions`), recursion is capped at roughly 5,000 frames by the host stack whatever `-z stack-size` says, and a warm compile is about 5 s. Budget problems accordingly.

### 2.2 Execution
- **Compile worker:** owns the clang module. Input: user source + harness + problem driver. Output: a WASM binary or diagnostics.
- **Run worker:** a fresh worker per run, with a WASI shim (e.g. `@bjorn3/browser_wasi_shim`, or a minimal in-repo shim) and stdin/stdout as in-memory buffers. Timeout via `worker.terminate()`. The wall time is reported. Optional instruction-count metering is not needed.
- **Time limits:** WASM is slower than native. Calibrate per problem: run the reference on the perf group in the browser and natively, and record the ratio. `timeLimitMs` = max(1000, 3 × the reference's WASM time on the slowest test), but always small enough that the problem's `wrong/tle_*.cpp` brute force exceeds it (checked natively in tests with a safety factor).
- **Verdicts:** AC, WA (first mismatching test, expected vs got, diff), TLE, RE (trap or abort message mapped to a friendly reason: out-of-bounds, stack overflow, `std::abort`), CE (raw clang output + friendly explanation from `lib/judge/clangErrors.ts`, built from errors captured by compiling known-broken snippets natively in tests).

### 2.3 LeetCode-style harness
- Problem signatures follow LeetCode conventions (`class Solution { public: vector<int> twoSum(vector<int>& nums, int target); };`).
- `lib/judge/harness/` provides `ListNode`, `TreeNode`, `Node` (graph), parsers and printers for LC literal formats (`[1,2,null,3]`, `[[1,2],[3]]`, `"abc"`, `true`) and a generated `main` per problem that reads the test input, calls the method, and prints a canonical output.
- Design-style problems ("LRU Cache") use the LC operations format (`["LRUCache","put","get"]`, `[[2],[1,1],[1]]`).
- Custom checkers (multiple valid answers, floating-point tolerance) are C++ or TS functions referenced from `meta.ts`.

### 2.4 Native verification (tests and CI)
`npm run content:verify` (and Vitest) does the following for every problem:
1. Compiles `solution.cpp`, `brute.cpp` and `wrong/*.cpp` with `g++ -std=c++20 -O2 -Wall` using the same harness.
2. Regenerates `tests.json` from `gen.ts` (seeded) with outputs from the reference. Generated files are committed, and the test fails if they're stale.
3. Stress-tests reference vs brute on 200 random small cases.
4. Asserts every `wrong/*.cpp` fails at least one hidden test (WA, or TLE beyond the safety-factored limit).
5. Validates `meta.ts` (patterns exist in the taxonomy, prerequisites exist, par time is set) and markdown structure (editorial sections present).

CI installs g++ (present on `ubuntu-latest`). Native compile results are cached by content hash in `.cache/` (gitignored) so the suite stays fast.

## 3. Content build

- Problems, cards, lessons and scrolls live under `content/`. A build script compiles them into per-region JSON chunks under `public/content/` (gitignored, generated in `prebuild`) or imports them statically. Choose and record an ADR, keeping first load small: regions load lazily.
- Lessons are MDX or TS objects with typed blocks (text, code, diagram, quiz, visualiser embed).

## 4. Game runtime

- `game/` holds the Pixi scenes: Overworld (tile map, player movement, NPCs, triggers, encounters), Battle (stage, sprites, FX), Transitions.
- `game/sprites/` holds palette + grid sprite definitions (as in Query Clash) with idle/attack/hurt/faint/evolve frames, `/dev/sprites` for review, and tests.
- `lib/battle/` holds the pure battle logic (damage, multipliers, hearts, verdict → animation events). It's unit-tested and has no Pixi dependency.
- `lib/srs/` holds the scheduler (mastery states, intervals, rust) with property tests.
- `lib/save/` holds the schema, migrations, export/import, and IndexedDB adapters.
- `lib/audio/` holds the WebAudio synth, the tracker format and SFX.
- `lib/dialogue/` holds the dialogue scripts (JSON/TS) with branching, portraits and flags.

## 5. Routes (initial plan)

`/` title + continue · `/play` overworld · `/battle/[id]` (also reachable from the overworld) · `/forge` · `/rift` · `/arena` · `/tower` · `/library` (codex, visualisers, cheat sheets) · `/journal` · `/trainer` (readiness report) · `/settings` · `/dev/sprites` · `/dev/judge` (a judge playground for testing the toolchain).

## 6. Budgets and quality gates

- First-load JS ≤ 300 KB gzip (before the toolchain). Check it with the build output in PROGRESS entries when it changes.
- Overworld at 60 fps on an iPhone 14 (Playwright mobile emulation as a proxy; no long tasks > 50 ms in the steady state).
- Warm compile + run of a typical solution ≤ 4 s on desktop.
- No console errors. No horizontal overflow on a 390 px width.
- Lighthouse PWA installable.
